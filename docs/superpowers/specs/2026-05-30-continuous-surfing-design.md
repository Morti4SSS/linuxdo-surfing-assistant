# Continuous Surfing Design

日期：2026-05-30

## 背景

Linux.do 的高价值信息不只来自最新帖或热门帖。老帖的新回复、低流量新帖、求助帖里的优质评论、经验分享贴的长期讨论，都可能对 AI 工具、skill、插件和工作流判断有价值。

因此“持续冲浪”的目标不是看完 Linux.do，也不是按时间线机械扫帖，而是让 Codex 在长任务里持续发现、排序、深读和沉淀高价值候选，直到候选质量收敛或预算耗尽。

## 目标

构建一个可被 Mac `/goal` 使用的持续冲浪循环，让 Codex 能跑更久，并且每一步都有明确输入、输出和停止标准。

这个能力要解决的问题：

- 用户不知道 Linux.do 里哪些帖子对自己有价值。
- Codex 单次冲浪容易看一小部分就停下，缺少可恢复队列。
- 新帖、老帖新回复、低流量神帖、求助帖优质评论都需要被纳入发现范围。
- 每轮阅读结果要沉淀下来，供下次继续和 skill 管理项目复用。

## 非目标

- 不做自动登录。Linux.do 登录态继续由 Codex 内置浏览器或已登录浏览器会话保存。
- 不做全站无差别爬虫。
- 不做 computer-use 通道。普通读帖不需要 computer-use。
- 不做无限无人值守后台任务。必须有预算、阶段性输出和停止条件。
- 不把持续冲浪和 skill 管理项目耦合。skill 管理只消费结果和证据包。

## 推荐方案：多队列淘金

持续冲浪使用多队列，而不是单一时间窗口或热度排序。

第一版保留三个主队列：

### 新帖队列

用途：

- 捕捉最近出现的新工具、新 workflow、新经验和新问题。
- 避免只读老帖导致错过新信号。

候选来源：

- 最近发布或最近出现在列表页中的帖子。
- 标题、标签、首帖摘要命中 AI、skill、workflow、MCP、CLI、Codex、Claude Code 等关键词的帖子。

### 活跃老帖队列

用途：

- 以老帖的新活跃作为入口，重新理解首帖、关键历史回复和近期回复的完整脉络。
- 覆盖经验贴、教程贴、争议贴、工具反馈贴。

候选来源：

- 最近有回复但创建时间较早的帖子。
- 回复数持续增加、点赞较高、或标题明显是经验分享/教程/踩坑/求助的帖子。

### 低流量抽样队列

用途：

- 避免只追热门，错过还没积累流量的高价值新帖。
- 给冷门标题、求助帖、工具自荐贴留探索预算。

候选来源：

- 浏览量、回复数不高，但标题或首帖命中强相关关键词的帖子。
- 求助帖、配置帖、工作流实践帖、插件/skill 自荐帖。

## 后续增强队列

以下队列不进第一版，但数据结构要允许后续扩展：

- 作者追踪队列：追踪高质量用户的近期帖子和回复。
- 评论引用扩展队列：从高价值回复里继续扩展被引用、被提到或被链接的相关帖子。
- 工具名反查队列：从已读帖里提取工具名、GitHub 链接、skill 名称和关键词，再反查相关讨论。
- Skill / workflow 证据队列：专门为 skill 管理项目收集社区反馈、对比、风险和推荐结论。

### 作者追踪队列

用途：

- 追踪高质量用户的近期帖子和回复，捕捉他们持续分享的工具、方法和判断。
- 从“好内容”反推“高信噪比作者”，再把作者近期活动作为候选来源。

触发来源：

- 某个帖子或回复被标记为高价值。
- 作者多次出现在高价值 reading 记录中。
- 作者回复中包含工具推荐、工作流复盘、踩坑修正、架构判断等强行动线索。

队列字段：

- `username`
- `profile_url`
- `source_topic_ids`
- `reason`
- `last_seen_at`
- `score`
- `cooldown_until`

选择规则：

- 只追踪和当前目标相关的作者，不做全站用户画像。
- 作者追踪有冷却时间，避免反复读取同一个作者的低价值动态。
- 追踪结果必须回落到具体帖子或回复，不保存泛化的人设判断。

输出：

- 该作者近期值得读的帖子或回复链接。
- 这些内容和当前 AI / skill / workflow 目标的关系。
- 是否应继续追踪、降低权重或移出队列。

### 评论引用扩展队列

用途：

- 求助帖和经验贴的评论区经常包含真正有价值的补充、反例和链接。
- 当回复里引用其他帖子、工具页面、GitHub 项目或关键术语时，把它们作为二跳候选，而不是读完当前帖就结束。

触发来源：

- 高价值回复包含 Linux.do 内链。
- 回复提到“之前有个帖子”“看这个方案”“某某工具/项目/配置”。
- 回复产生新的争议点、替代方案或风险点。

队列字段：

- `source_topic_id`
- `source_reply_id`
- `target_url`
- `target_type`：`linuxdo-topic`、`github`、`tool-site`、`keyword`
- `reason`
- `score`
- `depth`

选择规则：

- 默认只扩展一跳，除非二跳内容被评为高价值。
- 对 GitHub 和外部工具链接只记录待核验，不在 Linux.do 冲浪任务里深挖实现细节。
- 已读链接和明显重复关键词要去重。

输出：

- 扩展来源和被扩展目标的关系。
- 是否值得加入下一批深读。
- 提取到的工具、skill、workflow 或风险线索。

### 工具名反查队列

用途：

- 一个工具、skill 或 workflow 在单帖里出现时，单个观点不够可靠。
- 反查同名或近似名称，收集更多社区反馈、替代方案、风险和真实使用场景。

触发来源：

- reading 记录里出现工具名、skill 名、插件名、MCP server、CLI、GitHub 仓库名。
- 某个工具被多个帖子提到，但评价不一致。
- 用户的 skill 管理项目需要社区证据。

队列字段：

- `name`
- `aliases`
- `source_topic_ids`
- `source_urls`
- `category`：`skill`、`plugin`、`cli`、`mcp`、`workflow`、`library`
- `evidence_count`
- `positive_count`
- `negative_count`
- `score`

选择规则：

- 先用精确名称和常见别名反查，避免短名称误匹配。
- 对通用词、短词和容易撞名的工具降权，必须带上下文关键词。
- 反查目标是社区评价，不是替代 GitHub README 或官方文档。

输出：

- 正反馈、负反馈、对比对象、风险和试用建议。
- 是否适合同步到 skill 管理项目的社区证据包。
- 是否需要 GitHub 进一步核验。

## 长任务循环

`mac-goal` 通道执行的不是“随便继续看”，而是以下循环：

1. 刷新候选来源。
2. 将候选分配到新帖、活跃老帖、低流量抽样队列。
3. 按评分和配额选择下一批深读帖子。
4. 使用 Codex 内置浏览器阅读首帖、关键历史回复和近期高价值回复。
5. 输出结构化 reading 记录。
6. 提取新线索，更新候选队列。
7. 更新已读状态和本轮会话状态。
8. 判断是否继续下一批或停止。

## 队列配额

默认每批深读配额建议：

- 新帖队列：40%
- 活跃老帖队列：40%
- 低流量抽样队列：20%

如果某个队列不足，可以把剩余配额让给其他队列，但低流量抽样队列不应长期为 0。

## 评分信号

候选评分由多种信号组成：

- 标题关键词命中。
- 首帖或摘要关键词命中。
- 最近回复时间。
- 回复数、点赞数、浏览量。
- 是否属于求助、教程、经验、工具反馈、skill/workflow 讨论。
- 是否包含 GitHub、CLI、插件、MCP、skill、配置片段等可行动线索。
- 是否与已读帖子或已知工具重复。

时间和热度只能作为信号，不能作为唯一边界。

## 停止标准

持续冲浪默认使用混合停止标准：

- 达到本轮深读预算。
- 达到本轮粗筛预算。
- 连续若干批没有发现高价值候选。
- 三个主队列的高分候选都为空。
- 用户设置的 wall-clock 时间预算耗尽。

未读完但仍有价值的候选保留到 backlog，下次继续。

## 状态文件

第一版建议新增或扩展以下 JSON 文件：

- `state/linuxdo_surf_state.json`：继续保存已读 topic 和已同步 skill 名称。
- `state/linuxdo_frontier_queue.json`：保存多队列候选、分数、来源和下一批顺序。
- `output/linuxdo_surf/goal_task_<mode>.json`：给 `/goal` 使用的长任务说明。
- `output/linuxdo_surf/session_<timestamp>.json`：保存单次长任务的批次、阅读结果和停止原因。

状态文件要可恢复：如果 Codex 中途停止，下次可以从队列和已读状态继续，而不是从头开始。

## `/goal` 任务说明

工具生成的 `/goal` 说明应包含：

- 当前模式，例如 `goldmine` 或 `discover`。
- 操控通道：`mac-goal`。
- 候选队列路径。
- 已读状态路径。
- 本轮预算。
- 每批读取数量。
- 输出文件路径。
- 停止标准。
- 阅读和提炼格式。

Codex 在 `/goal` 中的责任是执行循环，不临场重新设计流程。

## 第一版验收

第一版持续冲浪能力验收标准：

- 能生成 `mac-goal` 长任务说明。
- 能维护新帖、活跃老帖、低流量抽样三个队列。
- 能从候选 topic 数据中按配额选出下一批深读候选。
- 对活跃老帖，能把新回复当成发现信号，但阅读时保留帖子历史上下文。
- 能记录每批阅读结果和停止原因。
- 连续运行不会重复选择已读帖子。
- 在候选不足或无高价值候选时能停止，而不是无限继续。

## 风险和处理

- 风险：候选数据源不完整，导致队列质量差。
  - 处理：第一版允许手动导入候选 topic 数据，后续再增强刷新来源。
- 风险：低流量抽样带来噪音。
  - 处理：限制低流量队列配额，并要求输出是否值得深读的判断。
- 风险：长任务输出过散。
  - 处理：每批必须写结构化 session 记录，最终只汇总高价值发现和后续 backlog。
- 风险：`/goal` 运行时上下文变长。
  - 处理：把状态写入文件，提示词只读取当前批次和必要摘要。

## 设计结论

持续冲浪应先做“多队列任务调度和状态恢复”，而不是先做更强浏览器自动化。`mac-goal` 的价值在于让 Codex 长时间执行一个可恢复循环；工具的价值在于给这个循环提供队列、预算和停止标准。
